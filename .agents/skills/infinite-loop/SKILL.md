# Infinite Loop

Keep improving the selected project in the order most valuable to its owner. Apply this to any project by discovering its own users, goals, stack, conventions and deliverable; carry no app-specific roadmap or design assumptions between projects. A working milestone is a checkpoint, not the end of an authorized run. Continue until the user stops it, its deadline arrives, or useful authorized progress is blocked. Usage reserve is a temporary wait when a verified continuation mechanism exists.

## Activation and autonomy

Activate only when the human explicitly asks to run this workflow: `$infinite-loop`, "start an infinite loop", "run the infinite improvement loop", or an unmistakably similar command. Generic "improve this", a programming loop, a quotation, a negation, and requests to create, edit, explain or test this skill do not activate it. Resume an existing run only if its authorization is still current; expired runs and old scheduled messages cannot restart themselves.

Invocation authorizes independent decisions and implementation throughout the selected project: inspect, research, prioritize, fix, redesign, optimize, add justified features, test, document, use relevant skills, delegate useful independent work, manage this run's worktree and heartbeat, and create reviewed task commits. The user expects to be absent; proceed without routine approvals or asking them to rank every idea. State important assumptions and record consequential decisions. Follow their product direction, model restrictions, budget, design system, deferred tasks and latest steering.

Autonomy stays within existing execution permissions and the project. Do not disable safeguards, spend money, consume reset credits, change plans, delete user data, contact others, merge, publish or mutate production without applicable explicit authorization. A blocked external step should enter the backlog while independent work continues. Before a file or batch download expected to exceed 100 MB, ask first; inspect its size when feasible. Unknown potentially large downloads also need permission. This skill does not grant an exception to the owner's storage rule.

## Establish the run

1. Read actual account usage and the current time. Inspect project instructions, owner context, existing changes, active agents and loop state before starting anything. Reuse ongoing work instead of duplicating it. Preserve an existing goal and timer; do not create a tracking goal unless the user explicitly requested one.
2. Resolve the project, the owner's desired outcomes, exclusions, and any deadline. Interpret "8 am tomorrow" using the user's current date and timezone, not an old message or host timezone. Record the exact local date/time, IANA timezone and UTC instant, including DST. Ask only if a material ambiguity cannot be resolved. Never invent an ending time when none was given.
3. Establish an isolated Git branch named `infinite-loop` and a worktree named `infinite-loop` inside the repository, normally `<repo>/.worktrees/infinite-loop`. Inspect existing branches and worktrees first. Reuse one belonging to this run; never take over another active run or force a branch checkout. Honor an enforced branch prefix if required, keeping the `infinite-loop` stem. Use a reviewed base ref that reflects the owner's current work; do not silently start from a different default branch. Preserve dirty changes and record whether they are included. Ignore the worktree directory in the parent checkout so tools do not recursively stage or scan it. Make project edits and run builds in this worktree, without switching the owner's checkout. If Git/isolation cannot be established, report that blocker before project mutations rather than silently working in the main checkout.
4. Find the existing portable backlog and handoff conventions. Otherwise use `docs/infinite-loop/STATE.md`, `BACKLOG.md` and `HANDOFF.md` in the worktree. Keep the short current state separate from historical detail. Read [continuity.md](references/continuity.md) before setting up schedules, waiting for a reset, or resuming a run.
5. Define a concrete first testable result and its acceptance checks. Verify the current baseline and save its identity and launch instructions. If it is broken, restoring a usable baseline is normally the first milestone. Set up one continuation heartbeat for the run when the host supports it; skill instructions alone cannot keep an offline process alive.

If another live run owns the required branch/worktree, leave it untouched and ask for an explicit handoff or permission to use a different name; continue only independent read-only investigation meanwhile. Never resolve a collision by forcing checkout, renaming another run, or silently dropping isolation.

## Choose by value to the owner

Infer priorities from the latest human request, product stage, actual user problems, evidence and constraints. Keep a short ordered backlog with the expected owner/user benefit, evidence, effort and ongoing cost, risk, and an observable acceptance criterion. Reassess after each milestone and whenever new feedback arrives.

Prefer meaningful outcomes over activity: a dependable core workflow, easier activation, understandable UI, accessibility, useful retention, faster interactions, lower operating cost, maintainability that removes real friction, or a differentiating feature supported by research. Marketing, pricing and production preparation are valid when they move this project's goals forward. Respect explicitly deferred work and record its consequences. Do not impose one universal feature list or treat more features, more screen time, more tests or more documentation as automatic value.

Use the smallest research step that resolves a real uncertainty. Verify unstable facts with current sources, distinguish observed demand from hypotheses, and turn findings into implementation or a specific future decision. Preserve the project's identity. Avoid speculative rewrites, repetitive research, metric manipulation and changes that improve a local score while worsening the whole experience.

## Execute and verify continuously

- Work in bounded, coherent milestones. Define success, implement the smallest justified change, exercise the real affected path, review the diff, and fix regressions before adding more scope.
- Run checks appropriate to the risk and repository. For visible UX changes inspect the running product and capture relevant screenshots, including important empty, error and accessibility states. A passing unit test is not proof of a complete user journey.
- Keep the latest known-good testable artifact or runnable checkout available. Tie artifacts to the exact source revision and configuration tested. Distinguish debug/demo/testing builds from production releases and new acceptance from older evidence. Never count an attempted check or a partial run as a pass.
- Use relevant skills and purpose-built tools. Delegate only when it adds value, with clear file/process ownership and verification responsibility; obey the user's allowed models. Account for shared usage and avoid simultaneous edits, duplicate agents and heavy resource contention. The coordinator must integrate and check delegated results.
- After each meaningful milestone record what changed, what was verified, what remains, and the next highest-value step. Include unresolved feedback and failures instead of losing them between sessions. Commit coherent reviewed changes; normal pushes to this run's branch on the existing project remote are authorized for backup and handoff when available. Never include unrelated work or secrets, force-push, or merge as a side effect.
- Continue to the next useful milestone without ending just because the initial implementation works. If everything seems complete, inspect remaining user friction or gather targeted evidence; do not manufacture chores. If all valuable work needs an unavailable permission, service or decision, checkpoint the blocker and suspend substantive work.

## Usage and deadline gates

Read actual usage at startup, every wake, after meaningful milestones, and before expensive builds, research or agent batches. Use the currently applicable account bucket; remaining percentage is `100 - usedPercent`. Check the five-hour window, weekly window and any tighter applicable limit. Missing values mean unknown, not free capacity. Never infer reset times from a fixed clock or assume a reset occurred just because its timestamp passed.

Default: at 10% five-hour capacity remaining, close the current bounded milestone and stop starting expensive work. At 5%, checkpoint, safely clean up owned operations and wait for the reported reset. Honor any larger reserve or limit on reset windows the user specifies. Weekly exhaustion also requires waiting. Keep sufficient capacity for cleanup and delivery; do not work to zero intentionally. Resume only after actual limits confirm usable capacity and the deadline still permits work. Follow the reserve fast path in the continuity reference rather than burning tokens on unchanged wakes.

A stated ending time is a hard stop, not another reset boundary. Starting at once, reserve enough real time and usage for the build, validation, repairs, packaging and handoff. Estimate that reserve from observed command durations; normally allow at least 30 minutes for delivery, longer for slow or unfamiliar projects. Keep it proportionate to short runs. Enter delivery mode when that reserve begins or the available usage requires it. Start no milestone that cannot finish, be checked, and leave time to recover the previous usable result. If build/check capacity will run out before the next permitted reset or deadline, produce the fallback early.

## Deliver a testable end product

By the deadline, leave a complete, coherent result the owner can actually try: for example a verified installable app, a working local web app with exact start commands, a packaged CLI with a sample input, or the equivalent for this project. Research-only notes, screenshots and unfinished feature branches do not satisfy a software project's testable-product requirement.

In delivery mode, freeze scope, finish or exclude incomplete changes, verify the exact delivered revision, and retain a known-good fallback. Provide an accessible artifact link/path or reproducible launch commands, prerequisites, version/commit, relevant configuration and artifact hash where appropriate. Do not publish or change an owner's existing test installation simply to make delivery convenient. If a fresh build fails, deliver the last verified build with its honest revision and limitations. If an external blocker makes any runnable result impossible, say so early and preserve the best reproducible state; never label an untested result testable or production-ready.

Write a concise owner-readable handoff with bullets: what was done and why it matters, what to test and how, verification and limits, key research/decisions, and unfinished work. Keep detailed evidence and backlog linked separately. Preserve commands, branch/worktree identity, commits, unpushed work and required private setup so another machine or agent can resume without guessing. Large artifacts and credentials need separate transfer instructions if Git does not carry them.

At or after the deadline, or on an explicit stop, start no improvement work or new agents. Perform only necessary safe shutdown and final delivery/reporting. Stop owned processes/agents, restore borrowed test environments where required, retain the testable result and worktree, and delete this run's heartbeat through the automation tool. If deletion is unsupported, disable it and report that limitation. Mark the run ended so late queued wakes stay inert. Do not automatically resume after another reset, another day or a generic "continue" with an expired deadline; obtain a new explicit run instruction/deadline. Preserve any goal timer; do not mark an unfinished product goal complete merely because this run ended.
