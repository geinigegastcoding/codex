# Android usage history and permission limits

## Findings for the current implementation

- Third-party apps have no documented Android SDK API to read Digital Wellbeing's own displayed totals or internal database. The supported public route is the generic `UsageStatsManager` API; it exposes system-maintained per-package usage aggregates/events, not a Digital Wellbeing export or guaranteed parity with its UI. Avoid claims that Ollo reproduces Digital Wellbeing exactly.
- `queryUsageStats(INTERVAL_DAILY, start, end)` gives package aggregates covering at least the requested range; Android may expand bounds to full interval boundaries. `totalTimeInForeground` is the app-provided aggregate, not an event-by-event exact stopwatch. Today is necessarily a partial/live bucket and can update between reads. A selected-app total is the sum of the selected package records, excluding Ollo and system/launcher/permission/settings/phone packages as product policy requires. Do not assume the API itself provides Ollo's desired exclusions.
- `queryEvents(start,end)` can reconstruct more detail from `ACTIVITY_RESUMED/PAUSED` (legacy `MOVE_TO_FOREGROUND/BACKGROUND` deprecated at API 29), screen interactive/non-interactive, keyguard, and startup/shutdown events. It requires the same usage access; system retains only a few days. Reconstruction must close intervals at screen-off/keyguard/background and handle overlapping activities, duplicate transitions, unknown start/end, and reboot. An unclosed interval across shutdown/startup has unknown end and should be dropped, not guessed.
- Missing access is a distinct state: `PACKAGE_USAGE_STATS` is special access enabled by the user in Settings, not an ordinary runtime permission. Verify it on return; handle `SecurityException`, null service/query (including locked user before first unlock on Android R+), empty list, and provider exceptions separately. Empty results are not evidence of zero use. Existing Ollo reader already gates on access, checks user-unlocked, and preserves unknown/partial states; it uses daily aggregates, not events.
- Calendar day bounds should be computed from local `LocalDate.atStartOfDay(ZoneId)` and the next local date, not fixed 24-hour milliseconds. DST days can be 23/25 hours. A timezone change changes which instants comprise “today”; retain/label the queried zone with the result. Current query is bounded by captured `now`, so it intentionally reports a partial current day.
- Ollo's local interval tracker uses wall and elapsed time plus boot count. Preserve those checks: elapsed time avoids wall-clock jumps within a boot; a reboot invalidates elapsed-time continuity; wall-clock/time-zone changes can shift calendar attribution. Android aggregates are epoch-based and may be expanded across boundaries; current `AndroidHistory` deduplicates cumulative snapshots and drops out-of-range/today-crossing buckets rather than prorating them. This is a conservative limitation, not a precise reconstruction.

## Permission UX that the platform supports

- Launch `Settings.ACTION_USAGE_ACCESS_SETTINGS` for Usage access and `Settings.ACTION_ACCESSIBILITY_SETTINGS` for accessibility. Android documents that a matching activity may not exist, so retain a fallback/clear recovery UI and recheck state after returning. Ollo already has both intents, a prior Accessibility disclosure/affirmative “Agree, open settings” action, and a usage access status row.
- Usage access requires user action in Settings. An accessibility service starts only after the user explicitly turns it on in device settings. Do not attempt to toggle either grant, use shell/system privileges, or automate Settings taps. Make the requested setting and purpose visible before leaving the app; give concise in-app visual steps if device Settings layout varies; allow dismissal and retry.
- Current Ollo service declares `canRetrieveWindowContent=false` and requests only window-state changes. Keep any disclosure aligned with this narrow behavior and its actual foreground-package use; no need to claim it reads screen contents.

## Browser/domain filtering boundary (feature research follow-up)

- `VpnService` can route IP packets through a user-approved VPN interface, set DNS servers/routes, and scope traffic by installed package with `addAllowedApplication`/`addDisallowedApplication`. Only one active VPN service/interface is available per Android user/profile; requesting Ollo's VPN can stop an existing VPN, and first use requires explicit system consent. Apps excluded from the VPN use ordinary networking. This is a material opt-in/network-scope cost, not a silent extension of current Accessibility access.
- DNS filtering can deny a queried hostname when the app's traffic uses DNS visible to the VPN. It is not a general URL filter: DNS names do not include HTTPS paths (`/shorts/...`, `/reel/...`), and DoH sends DNS queries inside HTTPS, so a DNS-only filter cannot inspect those queries. IP filtering is coarser still: multiple services/sites can share hosting/IPs, and blocking the address can break unrelated functions. Do not promise universal website blocking or reliable Shorts/Reels-only filtering from DNS/IP rules.
- HTTPS prevents a network VPN from reading URL paths/content without TLS interception; no benign public Android mechanism gives a consumer VpnService a browser's decrypted address bar/content. Selective Shorts/Reels detection is therefore a separate UI-recognition problem: Accessibility can inspect exposed view hierarchy only when `canRetrieveWindowContent=true`; current Ollo explicitly disables that. Recognition depends on app version, screen state and UI labels/structure, and can misclassify ordinary video, links or in-app browser surfaces. The old research note already treats it as compatibility-tested, separately consented work.
- Browser-address-bar Accessibility matching could read the user-visible URL only in browser UI states that expose it; it cannot reliably cover every browser, custom tab, hidden/scrolling address bar, embedded webview or non-UI navigation. It detects a displayed URL, not enforces all requests or page paths; pairing it with Accessibility overlay is friction/self-control, not a network security boundary.

Primary sources: [Android VPN guide](https://developer.android.com/develop/connectivity/vpn) (one active service per user/profile; consented service); [VpnService](https://developer.android.com/reference/android/net/VpnService) (one connection; `prepare()` consent/revocation); [VpnService.Builder](https://developer.android.com/reference/android/net/VpnService.Builder) (DNS, routes, per-app allow/deny semantics); [Android AccessibilityService guide](https://developer.android.com/guide/topics/ui/accessibility/views/service) (view hierarchy requires explicit `canRetrieveWindowContent` capability); [RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html) (DNS-over-HTTPS encapsulates DNS query-response in HTTPS).

## Calendar-day foreground reconstruction with UsageEvents (research addendum)

- Unlike `queryUsageStats(INTERVAL_DAILY)`, `queryEvents(begin,end)` takes inclusive/exclusive epoch-millisecond bounds and returns timestamped events without the documented whole-interval expansion. Public `ACTIVITY_RESUMED` / `ACTIVITY_PAUSED` events are API 29+ (`MOVE_TO_FOREGROUND` / `MOVE_TO_BACKGROUND` are the older, deprecated equivalents). `SCREEN_INTERACTIVE` / `SCREEN_NON_INTERACTIVE` are API 28+; `KEYGUARD_SHOWN` / `KEYGUARD_HIDDEN` and `DEVICE_SHUTDOWN` / `DEVICE_STARTUP` are API 29+. Query requires Usage access and data is retained only “a few days”; on Android R+ locked-user calls may return null.
- `UsageEvents.Event.getInstanceId()` would distinguish simultaneous instances of one activity, but AOSP marks it `@SystemApi` and `@hide`; it is not available to an ordinary public-SDK app. Public event pairing must use package/class and tolerate ambiguity. Do not depend on reflection/hidden APIs.
- `ACTIVITY_PAUSED` corresponds to `Activity.onPause()`, which can happen while still visible: Android explicitly documents paused activities remaining fully visible and a translucent foreground dialog can pause a partly covered activity. Conversely, Android 10+ multi-resume lets visible top activities in multiple windows remain resumed even when not focused. Thus public UsageEvents cannot produce an unambiguous exclusive “screen time” for every simultaneously visible package. A resume-to-pause duration is best labeled an estimate of resumed-activity time; it can undercount visible-but-paused apps and count unfocused resumed apps. Foreground service duration is not app UI time.
- Smallest truthful live-today strategy: query events from the prior local midnight through captured `now` (at least enough history to establish state at today's midnight), process in timestamp order, track resumed activities by package/class, clamp intervals to `[todayStart, now]`, and split every interval at local midnight using the captured `ZoneId`. Gate counting to screen-interactive and not-keyguard-shown; close all open intervals on screen-off, keyguard, shutdown, and end-of-query. Do not extend an interval through a reboot or infer a missing close. For multiple concurrently resumed activities, either union at device level and apportion package time only under an explicit deterministic rule, or report package activity-duration totals that may overlap; never call the latter exclusive device screen time. At `now`, include an open interval only as a live estimate and refresh it later.
- Unknown boundaries are unavoidable: if the earliest returned event is already inside an interval, the actual start is unknown; if query is empty, null, permission-rejected, or starts after the needed prior event was pruned, no valid zero can be inferred. A shutdown timestamp is the last persisted point, and AOSP documents that activity ends between shutdown persistence and startup are not saved; open pre-shutdown intervals without closes should be discarded. Wall-clock corrections can perturb event epoch times. Use local-day boundaries in the chosen zone (23/25-hour DST days), not fixed 24-hour arithmetic.
- Minimal acceptance tests: exact midnight split; already-open-at-query-start/retention cutoff => unknown; activity resume/pause normal closure; activity paused but still visible in split-screen (document undercount); simultaneous resumed activities (no exclusive sum assumption); screen-off/keyguard closure; reboot with unmatched open interval; query null/permission revoked/empty; local timezone and DST midnight boundaries; live interval refresh at captured `now`.

Primary sources: [UsageStatsManager.queryEvents](https://developer.android.com/reference/android/app/usage/UsageStatsManager#queryEvents(long,long)) (bounds, permission, retention, locked-user null); [UsageEvents.Event](https://developer.android.com/reference/android/app/usage/UsageEvents.Event) (event semantics/API levels); [AOSP UsageEvents](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/usage/UsageEvents.java) (`getInstanceId` is hidden `@SystemApi`); [Android Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle) (paused-but-visible); [Android multi-window and multi-resume](https://developer.android.com/develop/adaptive-apps/guides/support-multi-window-mode) (Android 10+ activities can remain resumed while unfocused).
