# Google SDK terms review: Ollo launch candidate

Date: 2026-10-19. Scope: the five `com.google.android.gms` coordinates flagged in the launch dependency audit. This is a bounded evidence note, not legal approval. Working tree source commit is `6f798f9`; inspected debug candidate APK SHA-256 is `b35661d1051d72381639e16f5a9f818a7b7997bc93bb7f2e0efc0d39160fb97f`.

## What the authoritative terms establish

The linked [Android Software Development Kit License Agreement](https://developer.android.com/studio/terms.html) describes the SDK to include Android system files, packaged APIs, and Google APIs add-ons (§1.1). It grants use to develop applications for compatible Android implementations (§3.1); limits copying, modifying, adapting, redistributing, decompiling, reverse engineering, disassembling, or making derivative works of the SDK except as third-party licenses require (§3.4); assigns components under open-source licenses solely to their own licenses (§3.5); and says not to remove or obscure proprietary rights notices contained in the SDK (§3.8). The agreement also says acceptance by someone acting for an entity requires authority to bind that entity (§2.4).

Google’s [Google Play services overview](https://developers.google.com/android/guides/overview) describes each Play services SDK as a lightweight client library included in an app which communicates with the full implementation in the Google Play services app. That explains the artifact shape but does not resolve how the SDK agreement’s redistribution language applies to Ollo’s app package. The POM label alone cannot answer that question.

The [official Play services API package index](https://developers.google.com/android/reference/packages) identifies the base, basement, location, places.placereport, and tasks package boundaries. The Places entry is a legacy client surface; Google’s [Places SDK API reference](https://developers.google.com/android/reference/com/google/android/gms/location/places/PlaceReport) identifies `PlaceReport` as a location-based report type. Ollo source does not call it, so no Places content is evidenced and no Maps/Places content attribution trigger is established here.

The candidate APK contains `assets/open_source_libraries.txt` (the five names are present) and `assets/open_source_licenses.txt` (12,704 bytes; current Apache 2.0, RevenueCat MIT, and CommonMark BSD text blocks). It does not contain the AARs’ `third_party_licenses.txt/json` as separate APK assets. The AAR catalogs list third-party components governed separately when their open-source licenses apply (consistent with SDK Agreement §3.5). This is a concrete local notice-audit lead: compare those catalogs with the final merged runtime components and current bundled notices, deduplicate by component/version, then include required notices. The AAR catalogs alone do not prove every listed component is incorporated into Ollo’s final APK or which notices are legally required.

Google’s [Play data disclosure page](https://developers.google.com/android/guides/play-data-disclosure) currently says the latest `base`, `basement`, and `tasks` SDKs listed there do not collect end-user data, but it is version-specific and does not cover Ollo’s older artifact versions or `location`/`places-placereport`. It cannot settle Ollo’s Data safety disclosures; those must follow the app’s actual calls, merged SDK versions, and data flows.

- **Actionable repository review before release:** perform a component-level comparison of the AAR embedded license catalogs with the final APK/runtime graph and existing `open_source_licenses.txt`; preserve/ship any applicable third-party notices. Recheck whether the dependency path can remove unused legacy `location`/`places-placereport` artifacts, but do not remove them based only on no direct source reference.
- **Owner or Google/licensor decision still required:** confirm who accepted the Android SDK License Agreement for the relevant legal entity and their authority under §2.4; determine whether the client AAR distribution inside Ollo’s user-facing APK is covered by the granted app-development use or raises a §3.4 redistribution question; confirm any proprietary notice needed under §3.8. The Android SDK terms and artifact POMs do not answer these product-specific points. Do not label the five as Apache/MIT or close the launch gate without that determination.
