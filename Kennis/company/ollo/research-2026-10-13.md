# Ollo — blocker, UI and Android research

Research dates: 13–14 October 2026. Repository: [geinigegastcoding/Ollo](https://github.com/geinigegastcoding/Ollo), private. This is an Android product; iOS references below inform hierarchy and feedback, while the implementation retains native Android controls.

## Recommended direction

Make Ollo a calm, local companion that interrupts automatic scrolling while keeping useful functions accessible. The strongest near-term combination is **intentional opening + a finite learning exercise + reliable selected-app blocking**. Preserve calls, alarms and Android permission controls. Describe protection limits and missing measurements honestly.

The opening quiz, icon-derived mascot and screen refinement are implemented in 0.2.0-review. Selective Shorts/Reels blocking, notification control, widgets and the other ideas in this report are proposals, not active features.

## A useful GitHub reference for Shorts and Reels

The best inspected reference is [atick-faisal/Shorts-Blocker](https://github.com/atick-faisal/Shorts-Blocker), inspected at commit `b859d973e66402fb113330e53cd0a6168478a9fa`. GitHub reports Apache-2.0, and the inspected Kotlin files include that license header. Its service separates platform detectors, listens for window/subtree changes, scopes watched packages, and applies a 1.5-second action cooldown. Those are useful design patterns. [Service source](https://github.com/atick-faisal/Shorts-Blocker/blob/b859d973e66402fb113330e53cd0a6168478a9fa/app/src/main/kotlin/dev/atick/shorts/services/ShortFormContentBlockerService.kt).

**Use this as a reference, not a drop-in reliability guarantee.** The YouTube detector searches at most 120 nodes for `reel_progress_bar`; despite its comment, it does not check visibility. The Instagram detector scans only ten nodes and can treat the absence of `feed_tab` as a positive match. That could also describe unrelated screens. Its own comments mention false positives and older supported app versions. [YouTube detector](https://github.com/atick-faisal/Shorts-Blocker/blob/b859d973e66402fb113330e53cd0a6168478a9fa/app/src/main/kotlin/dev/atick/shorts/services/detectors/YouTubeShortsDetector.kt), [Instagram detector](https://github.com/atick-faisal/Shorts-Blocker/blob/b859d973e66402fb113330e53cd0a6168478a9fa/app/src/main/kotlin/dev/atick/shorts/services/detectors/InstagramReelsDetector.kt).

### Ollo's next selective-blocking implementation

This is an engineering proposal derived from the source review:

1. Keep the current package-based blocking path. Add an explicit, separate opt-in for inspecting supported app interfaces, with updated disclosure and consent.
2. Use view IDs, visibility, selected state and a positive combination of markers. Do not infer Reels merely because a normal-feed marker is absent. Avoid reading or storing message text.
3. Inspect only the supported foreground application. Bound node visits, depth, queued children and elapsed processing time. Use deterministic selectors and cooldowns.
4. Show a compatibility status for each supported app/version. Missing markers or an unsupported version should produce an honest “not verified” state rather than a claim of successful protection.
5. Test Reels tabs, swipe feeds, direct links, DMs containing a reel, ordinary posts, stories, search, normal YouTube videos, Shorts shelves, picture-in-picture, split screen and both Dutch/English interfaces.
6. Test the return action as well as detection: a marker must not cause a repeated Back loop or close useful content. Store aggregate outcome counts, not the captured hierarchy.

Ollo currently declares screen-content retrieval **off**. Expanding that capability changes the privacy contract and needs its own consent and acceptance work. Android exposes capabilities and view-ID reporting through AccessibilityService configuration; this is not arbitrary access to another app's database. [Android service configuration](https://developer.android.com/guide/topics/ui/accessibility/views/service).

## Features a dependable blocker should cover

This checklist combines common competitor capabilities with Ollo-specific product judgment. “Should cover” does not mean every feature must be implemented in the first release.

| Capability | Why it matters | Ollo status / priority |
|---|---|---|
| Explicit app selection, real app icons and search | The user must know exactly what a rule affects | Present |
| Essentials / allowed apps | Blocking should leave necessary work available | Present, with safety packages |
| One-tap timed focus block | Low effort for a spontaneous reset | Present: ten-minute pause and Quick Settings tile |
| Recurring schedules, weekdays, overnight blocks, timezone and DST | Real routines cross midnight and travel | Present; domain regression tests |
| Per-app daily budgets and a combined distraction goal | Different apps have different roles | Present |
| Session limits and re-intervention | An intentional opening can still become a long scroll | Present: session budget and break |
| Soft decision points and fixed blocks | Users need different commitment strengths | Present; no claim that Android Settings can be locked |
| Visible opening delay and brief return grace | Add friction without punishing a quick useful switch | Present |
| Finite learning gate | Convert an automatic opening into three deliberate answers | Added: math, chess and sourced facts |
| A clear reason and countdown on the block screen | The user should understand what is happening | Present |
| Narrow emergency access | One urgent app should not disable all rules | Present: app-specific two-minute grant |
| Calls, alarms and system recovery remain reachable | Avoid a lockout during an urgent need | Present; physical-device acceptance still matters |
| Reliable status and permission repair | A disconnected service must not be displayed as protection | Present |
| Conservative history, coverage labels and text chart values | Missing data must not become fake success | Present |
| Export, measurement deletion and local privacy controls | The user retains control of their data | Present |
| Reboot, screen-off and clock-change recovery | Focus timers should survive ordinary device events | Present; monotonic timer logic |
| TalkBack labels, large text, keyboard insets and system Back | The complete flow must stay usable | Native controls; emulator review and hardware checklist |
| Selective Shorts/Reels blocking | Keep messages and useful videos available | Next major feature, behind compatibility tests |
| Website / path blocking | Browser distraction can bypass app-only rules | Later, explicitly supported browsers or extension |
| Optional pre-limit reminder | End a session intentionally rather than abruptly | High-value next addition |
| Home-screen widget | Start protection without opening the app | High-value next addition; tile already exists |
| Optional notification quieting | Notifications can restart the habit loop | Later; separate Android access and disclosure |
| Open-count limits and intention outcomes | Target repeated checking, not only total minutes | Later; first define a trustworthy session boundary |
| Accountless backup/import | Useful across phone replacement | Later; current export does not imply a tested restore flow |

The comparison was grounded in [one sec's manual and scheduled blocks](https://tutorials.one-sec.app/en/articles/3311298), [one sec's intervention modes](https://feedback.one-sec.app/help/articles/1693386-immediate-vs-delayed-vs-always-ask-which-one-is-the), [its intentional switching and re-intervention documentation](https://feedback.one-sec.app/help/collections/1564268-configuration-and-features), [Jomo's rule overview](https://help.jomo.so/en/article/how-to-start-with-jomo-mseknq/), [AppBlock's schedules](https://appblock.app/help/android/schedules/) and [AppBlock's settings](https://appblock.app/help/android/settings/). Those products' stricter-lock marketing does not establish what a normal Ollo installation can or should enforce.

## What Android system access can actually do

| Access / API | Useful capability | Material limit / decision |
|---|---|---|
| UsageStatsManager with user-granted usage access | Historical app usage and budget inputs | Not itself an enforcement mechanism; provider coverage can be partial. [Android usage API](https://developer.android.com/reference/android/app/usage/UsageStatsManager) |
| AccessibilityService | Foreground changes, an accessibility overlay, and deliberate Back/Home actions | Current Ollo uses package changes without screen-content retrieval. Selective UI matching needs additional capability and consent. [Android AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) |
| Accessibility overlay | A blocking or opening surface above the selected app | It is voluntary self-control, not a device-wide security boundary. Retain system controls and recovery. [Android overlay API](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_ACCESSIBILITY_OVERLAY) |
| VPN / DNS | Domain-level network filtering | Encrypted URL paths and shared hostnames prevent a dependable “Shorts only” rule; Android permits one active VPN per user/profile. [Android VPN guide](https://developer.android.com/develop/connectivity/vpn) |
| DevicePolicyManager | Package suspension in an appropriately managed device/profile | Device/profile-owner or delegated management authority is not an ordinary consumer permission. Do not request it as a shortcut. [Device policy API](https://developer.android.com/reference/android/app/admin/DevicePolicyManager) |
| Notification policy access | An optional quiet focus rule | Requires separate access. Modern target versions use app-associated AutomaticZenRules for these changes; restore the user's intended state. [NotificationManager](https://developer.android.com/reference/android/app/NotificationManager) |
| Quick Settings and AppWidgetProvider | Start an existing pause directly | Reuse the controller. A widget should not claim exact real-time background measurement. [Android widgets](https://developer.android.com/develop/ui/views/appwidgets/overview) |

Google Play requires appropriate declaration and prominent disclosure/consent for a non-accessibility-tool app using AccessibilityService. It restricts preventing users from disabling/uninstalling services and bypassing platform security controls, except specified managed/parental circumstances. Keep `isAccessibilityTool=false`, keep settings reachable, and assess any new permission against the exact feature. Store approval is not established by passing builds. [Google Play sensitive API policy](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en).

## Distinctive, feasible next features

These are product proposals, not measured user demand or active functionality:

1. **A small offline learning habit.** Grow the existing finite quiz with difficulty choices and curated spaced repetition. Keep it brief; no feed, streak pressure or penalty for choosing an essential app.
2. **“Messages, not the feed.”** Add carefully verified Reels/Shorts protection while showing the exact supported app version and what remains available. This is more useful than promising universal interception.
3. **A purpose and a finish time.** Let a user choose “reply”, “look something up” or another intention and a short session budget. Return to that intention before a new session starts.
4. **Gentle end-of-session notice.** Offer a brief warning before the existing pause, with the hard boundary unchanged. It supports finishing a useful action.
5. **Protection confidence.** A compact status showing service connection, measurement coverage and selective-rule compatibility can distinguish Ollo through honesty and repairability.
6. **A tiny home-screen companion.** Show the icon-derived mascot, an actual active timer and a one-tap pause. Use real state; do not imply that a cartoon mood diagnoses the user.
7. **A voluntary reflection after a session.** Ask whether the opening was useful and show the user's own pattern over time. Do not infer emotions or claim saved time from unobserved activity.

Recommended sequence: finish physical-device acceptance for this release → pre-limit reminder/widget using existing controller actions → separately consented selective-blocking prototype with app-version tests → only then consider notification or browser access. No cloud model is needed for routing, grading, retries or enforcing any of these deterministic rules.

## Quiz content and mascot provenance

Math is generated and graded locally with integer arithmetic. The three chess boards have one legal mating move each, checked with python-chess during development; there is no chess-engine dependency in the Android app. Facts are curated, locally bundled and sampled without repetition inside one opening session. An incorrect answer never opens the target, and the final action still asks for a conscious opening.

Fact sources: [Venus rotation and orbit](https://science.nasa.gov/venus/venus-facts/), [sunlight travel time](https://science.nasa.gov/learn/basics-of-space-flight/chapter1-1/), [lunar recession](https://eclipse.gsfc.nasa.gov/LEcat5/secular.html), [Saturn density](https://science.nasa.gov/saturn/facts/), [Mercury polar ice](https://nssdc.gsfc.nasa.gov/planetary/ice/ice_mercury.html), [Earth's size among rocky planets](https://science.nasa.gov/earth/facts/). The Venus question specifies rotation rather than conflating a sidereal rotation with a solar day.

The new transparent mascot was generated with the built-in ImageGen tool from a rendering of the existing launcher icon. Final asset: `app/src/main/res/drawable-nodpi/ollo_mascot.png`. Production packaging downsizes the generated asset to 512×512 while retaining alpha. The launcher icon itself is preserved.

The generation requested a compact waving orange pixel creature with the icon's square white eyes and charcoal features, transparent alpha, and no mask or nighttime costume. [Full generation prompt and provenance](https://github.com/geinigegastcoding/Ollo/blob/main/docs/MASCOT.md).
