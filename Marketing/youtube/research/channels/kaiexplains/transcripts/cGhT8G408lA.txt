The agent never notices the difference. So, why is Kimi K3, or any large model, slow? Because it writes one token at a time. To produce a single word, it runs the entire network, gets one token back, then does it all over again for the next. Every word is a full round trip. Speculative decoding breaks that rule. A small, fast draft model sprints ahead and guesses the next several tokens. Then the big model checks all those guesses in one pass. The right ones are kept for free. It is spell check for the future. But classic speculative decoding has a weakness. The draft is dumb, so the big model rejects a lot of guesses, and every rejected guess is wasted work. Push too hard, and you actually slow down. How big is the win with DSpark, really? On Kimi K3 and VLM, with DSpark enabled, throughput goes from 118 tokens per second to 370. That is a 3.14 times improvement on a single request, measured on Nvidia GB300 hardware. On coding and other low entropy tasks, the draft model gets accepted about 4.73 tokens per step. On creative writing and other high entropy tasks, it drops to around 2.61. The win scales with how predictable the work is. Code is predictable. Deep Spark rewards that. Deep Spark attacks the bottleneck from three angles at once. A block diffusion backbone drafts seven tokens in a single parallel pass, not one by one. A lightweight Markov head stitches those tokens together so they read like a real sentence, not a random bag. And a confidence head scores how likely each guest token is to survive, so the engine only bothers verifying the ones worth checking. It literally decides what not to verify. Skip the sure things, spend the compute where it counts. And remember, none of this changes the answer. The verification step guarantees the output is exactly what the model would have written token by token. You are not trading quality for speed. You are getting the speed for free. Here's why these two belong together. Infra Act built the Kimi K3 Deep Spark draft model to mirror K3's own MLA attention design, which means the draft and the target share one KV cache layout. The draft was trained on hidden states extracted from VLLM itself, the same engine that serves it. So the numerics it learns from are the numerics it meets at inference.
